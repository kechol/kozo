---
title: コンセプト
description: 依頼が kozo の中をどう進むか、何があなたを待つか、自律度がどの承認を求めるかを説明します。
---

kozo は、1 人のためのソフトウェアファクトリーです。依頼を渡すと、差分 1 つで済む大きさのタスクに切り分け、タスクごとに実装と確認を済ませて、読んでマージできる差分を返します。あなたの仕事は、方針を決めること、inbox を片付けること、マージすることです。

## 構成

| 部品               | 内容                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| kozod              | 常駐するプロセスです。コードで決められる判断をすべて行い、状態をすべて書き、`127.0.0.1:7420` で local API を提供します。             |
| `kozo`             | コマンドラインです。状態を持たず、local API を呼ぶだけです。                                                                         |
| ダッシュボード     | inbox、board、詳細画面のあるローカルの Web ページです。`kozo` と同じく、local API を呼ぶだけです。                                   |
| エージェント       | 役割が 1 つずつ決まった Claude Code のセッションです。triage、plan、implement、review、verify と、質問に答える explorer があります。 |
| factory definition | `~/.kozo/factory` にある git リポジトリで、`factory.yml`、agents、skills、blueprints、automations が入っています。                   |
| Charter            | 各リポジトリの `.kozo/charter.yml` で、そのリポジトリで kozo がしてよいことを決めます。変えるのは人だけです。                        |
| constraints        | 各リポジトリの `.kozo/constraints.yml` で、変更を確かめる gate とコマンドを決めます。                                                |

モデルが担うのは、分類、計画の下書き、実装、レビューだけです。振り分け、上限、予算、確認といったほかの判断は、すべて kozod のコードが行います。

## item と task

**item** は 1 件の依頼です。`kozo add` で追加したもの、GitHub モードの Issue、automation が決まった時刻に追加したものがあります。reference は `K-<n>` で、Issue なら `<repository>#<n>` です。

**task** は item を切り分けたもので、差分をちょうど 1 つ作ります。reference は `K-3/t1` のような `<item>/t<n>` です。タスクごとに、最新のデフォルトブランチから専用の git worktree を作り、`kozo/<factory ID>/<item>-t<n>` という名前のタスクブランチで作業します。

**run** は、item か task のためにエージェントのセッションを 1 回動かしたものです。reference は `r-<nnnn>` です。

## stage

item と task は同じ stage を進みます。

| stage     | 起きること                                                                                                                                                                        |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Intake    | kozod が、リポジトリの Charter の準備ができているかを確かめます。自律度が求めるなら、item を開始の承認待ちにします。                                                              |
| Triage    | triage エージェントがリポジトリを変えずに読み、計画を下書きします。計画には、work class、risk tier、方針、完了の条件（DONE_WHEN）、タスクが入ります。kozod が下書きを確かめます。 |
| Planning  | 計画があなたの承認を待ちます。差し戻しや回答のあとは、plan エージェントが書き直します。feature の場合は、先にあなたと受け入れ条件を詰めます。                                     |
| Building  | 各タスクを worktree で実装し、gate、prove、diff-guard を通します。                                                                                                                |
| Reviewing | 別のセッションの review エージェントが、タスクの目的と DONE_WHEN だけに照らして差分を判定します。verify エージェントはアプリを操作して、証拠を残します。                          |
| Handoff   | タスクを最新のデフォルトブランチに rebase して、もう一度確かめます。kozod が handoff report を書き、差分があなたのマージを待ちます。                                              |
| Complete  | マージのあと、kozod がマージ後のデフォルトブランチで gate を実行します。item は、すべてのタスクが完了すると完了になります。                                                       |
| Cancelled | あなたが item か task を取り消しました。                                                                                                                                          |

開いている item や task は、`kozo close <ref> --done` か `--cancel <reason>` で、いつでも自分で閉じられます。

## hold

**hold** は、item や task が進まない理由です。1 つの item や task が同時に持つ hold は 1 つまでで、stage とは別に記録されます。

| hold       | 待っている理由                                                                            | 外し方                                                                   |
| ---------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| approval   | 開始か計画に、あなたの承認が要ります。                                                    | `kozo approve <item>`。計画なら `kozo reject <item> <reason>` も使えます |
| question   | エージェントが質問したか、review が判断を人に回したか、変更が保護されたパスに触れます。   | `kozo say <ref> <answer>`                                                |
| attention  | タスクが上限で止まったか、kozod が run を見失ったか、ブランチがマージされずに消えました。 | `kozo retry <ref>` か `kozo close`                                       |
| paused     | あなたが `kozo pause <ref>` で止めました。                                                | `kozo resume <ref>`                                                      |
| taken      | あなたが `kozo take <task>` で、タスクを自分で作業しています。                            | 作業をコミットしてから `kozo return <task> <text>`                       |
| dependency | ほかの item か task の完了を待っています。                                                | それが完了すると、kozod が外します                                       |
| capacity   | backpressure、1 日の予算、同時実行数のせいで始められません。                              | 余裕ができると、kozod が外します                                         |

## inbox

**inbox** は、あなたを待っているものを古い順に並べたものです。承認、質問、attention、マージを待つタスクが入ります。`kozo ls` とダッシュボードのどちらでも見られます。kozo の日々の運用は、inbox を片付けることです。

## 自律度

Charter は work class ごとに L1、L2、L3 のいずれかの自律度を決め、item に要る承認はこれで決まります。自分の自律度を持たない class には、`levels.default` が使われます。

| 自律度 | 開始の承認 | 計画の承認                                                                 |
| ------ | ---------- | -------------------------------------------------------------------------- |
| L1     | 要る       | 要る                                                                       |
| L2     | 要らない   | 要る                                                                       |
| L3     | 要らない   | タスクが複数ある計画、risk tier が high の計画、codemod を含む計画だけ要る |

次の item は、自律度に関係なく、いつも両方の承認が要ります。

- automation が追加した item。
- GitHub モードで、リポジトリへの書き込み権限がない人の Issue、またはリポジトリを登録する前に開かれた Issue。

triage が、依頼で指定した class より低い自律度の class を下書きしたときは、低いほうが使われます。

kozo が自分で自律度を変えるのは、下げる方向だけです。マージ後に不具合が見つかったとき、または直近 10 件のマージ済みの差分のうち 30% を超えてあなたの手が入ったとき、そのリポジトリのその class の自律度を 1 段下げます。下げた状態は、あなたが Charter を変えるまで続きます。上げるのはいつもあなたです。L2 の class で、直近 20 件のマージ済みの差分に人の手が入らず不具合もなかったときは、`kozo report --review` が L3 を提案します。Charter に書くかどうかは、あなたが決めます。

## work class

計画の work class が、タスクが Building から Handoff まで従う blueprint を決めます。

| class     | blueprint が求めること                                                                                                                          |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| bugfix    | 修正がないと失敗するテストを先に書きます。                                                                                                      |
| feature   | 新しい振る舞いを確かめるテストを、変更がないと失敗する形で先に書きます。                                                                        |
| refactor  | 振る舞いを変えません。既存のテストは通り続け、追加したテストも変更なしで通ります。                                                              |
| perf      | 振る舞いを変えず、full の gate で確かめます。                                                                                                   |
| deps      | 再現のテストは要らず、deep の gate で確かめます。                                                                                               |
| docs      | 再現のテストは要りません。                                                                                                                      |
| migration | 1 本の鎖になったタスクで進め、最初のタスクはテストを足すだけです。タスクに codemod があれば実装の前に実行し、各段階で deep の gate を通します。 |

## 変更の確かめ方

どの差分も、安いものから高いものの順に同じ層を通ります。

| 層            | 確かめること                                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| V1 gates      | lint やテストなど、constraints にあるリポジトリ自身のコマンドを、fast、full、deep のいずれかの水準で実行します。               |
| V2 diff-guard | 差分の大きさ、scope、保護されたパス、既存のテストの書き換え、無効にされたテストを調べます。                                    |
| V3 prove      | テスト以外の変更を戻したとき、変えたテストが失敗することを確かめます。振る舞いを変えない作業では、通り続けることを確かめます。 |
| V4 review     | 差分と元の指示だけを見る、別のセッションです。                                                                                 |
| V5 verify     | `.kozo/verify-app.md` の手順でアプリを動かし、証拠を残すエージェントです。                                                     |

計画の risk tier が深さを決めます。low のタスクは fast の gate を通して review で終わり、normal は full の gate、prove、verify を足し、high は deep の gate を通します。kozod は、タスクの scope が保護されたパスに届くときなどに計画の risk tier を上げることはありますが、下げることはありません。

## マージはいつも人が行う

kozo には、マージする機能がありません。local モードではあなたがタスクブランチをマージし、GitHub モードでは kozod がブランチを push して pull request を開き、あなたがそれをマージします。エージェントは GitHub の認証情報を持たず、自分の worktree の中にしか書き込めません。push するのは kozod だけで、すべての確認を通ったあとに限ります。

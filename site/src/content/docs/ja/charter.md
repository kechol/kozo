---
title: Charter
description: .kozo/charter.yml のすべてのキーと、リポジトリで kozo がしてよいこと、各上限に達したときに起きることを説明します。
---

Charter（`.kozo/charter.yml`）は、1 つのリポジトリで kozo がしてよいことを決めます。変えるのは人だけです。kozo はこれをデフォルトブランチ（GitHub モードでは `origin` のもの）の先端から読み、差分からは読みません。テンプレートでは、Charter 自体も保護されたパスです。

どのキーにも既定値はありません。キーが欠けていたり綴りが違っていたりすると Charter を読めず、kozo はそのリポジトリで作業しません。

```yaml
version: 1
status: ready
isolation: worktree
protected_paths:
  - '.kozo/**'
  - '.github/**'
  - '.claude/**'
  - 'AGENTS.md'
  - 'CLAUDE.md'
existing_tests_protected: true
levels:
  default: L1
  docs: L2
limits:
  max_changed_lines: 400
  max_files: 8
  max_tasks_per_item: 8
  inner_retries: 2
  ci_fix_rounds: 2
  no_progress_rounds: 3
  max_turns: 40
  max_minutes: 45
  max_cost_usd: 5
backpressure:
  max_awaiting_merge: 3
  max_held: 10
```

上の値はテンプレートのものです。

## `version` と `status`

| キー      | 意味                                                                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version` | いつも `1` です。                                                                                                                                                      |
| `status`  | `ready` か `incomplete`。`ready` になるまで、kozo はそのリポジトリで新しい item を受け付けず、automation を飛ばし、タスクを始めません。`kozo check` は警告を出します。 |

## `isolation`

`worktree` では、各タスクが専用の git worktree で作業します。スキーマは `docker` も受け付けますが、kozo は実装しておらず、何も変わりません。

## `protected_paths`

kozo が人の手を離れて変えることのないパスです。各パターンは glob としても文字どおりのパスとしても扱われ、一致したものの下にあるものすべてに及びます。そのため `src/config`、`src/config/`、`app/[id]` のどれも、その中身を守ります。

- エージェントは保護されたパスに書き込めません。先へ進むには、そのことを質問するしかありません。
- 保護されたパスに触れる差分は、あなたへの質問で止まります。
- タスクの scope が保護されたパスに届く計画は risk が high になり、いつもあなたの計画の承認が要ります。

## `existing_tests_protected`

`true` のとき、デフォルトブランチにあるテストのファイルは変更も削除もできません。エージェントは書き込めず、それを変える差分は diff-guard が拒みます。新しいテストのファイルは、いつでも追加できます。どれがテストかは、[constraints](../constraints/) の `tests` で決まります。

## `levels`

work class ごとの自律度で、`L1`、`L2`、`L3` のいずれかです。`default` は必須で、自分のキーを持たない class（`docs`、`deps`、`bugfix`、`refactor`、`perf`、`migration`、`feature`）に使われます。それぞれが求める承認は、[自律度](../concept/#自律度) を参照してください。

不具合が見つかったり人の手が頻繁に入ったりすると、kozo は class の自律度を下げることがあります。下げた自律度は、あなたが Charter を変えるまで続きます。

## `limits`

数は 1 以上の整数です。`inner_retries` と `ci_fix_rounds` は 0 にもでき、その場合は最初の失敗でタスクが止まります。

| キー                 | 上限の対象                                                                                                                                                 | 達したとき                                                                                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `max_changed_lines`  | 1 つのタスクの差分で変わった行数。生成ファイルは除きます。                                                                                                 | これを超える見積もりの計画は書き直しに回され、下書きが 2 回拒まれると item があなたの対応を待ちます。これを超える差分は、あなたへの質問で止まります。          |
| `max_files`          | 1 つのタスクの差分で変わったファイル数。生成ファイルは除きます。                                                                                           | `max_changed_lines` と同じです。                                                                                                                               |
| `max_tasks_per_item` | 1 つの計画のタスク数。                                                                                                                                     | 計画は書き直しに回され、下書きが 2 回拒まれると item があなたの対応を待ちます。                                                                                |
| `inner_retries`      | review や verify がタスクを Building に戻せる回数。                                                                                                        | タスクがあなたの対応を待ちます。review が判断を人に回したときは、すぐに質問になります。                                                                        |
| `ci_fix_rounds`      | 最後の確認に失敗したとき、または GitHub モードで pull request のチェックが失敗したときに、タスクが Building に戻る回数。                                   | タスクがあなたの対応を待ちます。`kozo retry` で回数が戻ります。                                                                                                |
| `no_progress_rounds` | 1 回の作業のループでの試行の回数。試行のたびに、brief から始まる新しいセッションになります。                                                               | タスクがあなたの対応を待ちます。                                                                                                                               |
| `max_turns`          | 1 つのエージェントのセッションのターン数。                                                                                                                 | タスクか item があなたの対応を待ちます。                                                                                                                       |
| `max_minutes`        | 1 つのエージェントのセッションの分数と、各コマンド（services、prepare、各 gate、prove、codemod）の分数。                                                   | 時間切れのセッションは、あなたの対応を待ちます。コマンドは止められて失敗として扱われるので、時間切れの gate はほかの失敗した gate と同じようにやり直されます。 |
| `max_cost_usd`       | 1 つのエージェントのセッションが使える金額（ドル）。review、verify、explorer も含みます。kozod は、動いている作業ごとにこの額を 1 日の予算から確保します。 | タスクか item があなたの対応を待ちます。                                                                                                                       |

## `backpressure`

あなたが追いつくまで、そのリポジトリで新しい作業を止めるための上限です。どちらかに達している間は、そのリポジトリで新しいことを始めません。triage も書き直しも行わず、タスクは capacity で待ちます。上限を下回ると、kozod がこれを外します。

| キー                 | 数えるもの                                             |
| -------------------- | ------------------------------------------------------ |
| `max_awaiting_merge` | すべての確認を通り、あなたのマージを待っているタスク。 |
| `max_held`           | 質問か、あなたの対応を待っている item とタスク。       |
